### The invoice, checked on live data

Thirteen completed bookings were chosen on production to cover every case that
has ever gone wrong on a bill — extra km, extra hours, toll, parking, GST
recorded, **no** GST recorded, advance paid — and each one's invoice was fetched
**through the live endpoint** with a signed link, the same PDF the app's Invoice
button opens. Parsed and checked against the database row, not against the
renderer's own arithmetic:

```
13 live invoices · 83 checks · 83 passed · 0 failed
```

What those checks cover: the final amount equals the fare charged; the tax rate
printed multiplies the taxable value up to the tax charged; CGST + SGST equals
the GST the booking recorded; extra km and extra hours bill at exactly qty ×
rate; toll and parking are paid back at the amount laid out; and every printed
per-km rate multiplies out to its own line.

The client's complaint, on a real bill (`CB2521991114`):

```
Cab Service (Best Price) - Soila to Kherapa (16 km)   Rs. 12.44/km    199.00
Discount (20%)                                                       -40.00
Extra 7 km                                           Rs. 12/km        84.00
CGST                                                 2.52%             4.00
SGST                                                 2.52%             4.00
Total                                                                251.00
```

199 − 40 + 84 + 4 + 4 = **251**, which is the fare the booking stored. Before
this deploy the tax rows printed *today's* Pricing Config rate — 6% against a
₹4.00 figure — and the extra-km line was divided by 1 + GST% on any booking
with no GST recorded, so the same ₹84 charge printed as ₹75. Both are gone.

The PDFs fetched for this check were deleted from the server afterwards.

### The auth change, checked against live data

`findUserByMobile` matches on the last ten digits, so it was worth knowing
whether any live number is already stored two ways — the lookup returns one
document and would have to choose.

```
7,345 users · 0 numbers written more than one way · 0 with money on both sides
```

Nothing on production can be mis-resolved by this change; it only stops the
second account from being created in future.

> One verification was **not** done: posting to `/auth/login/send-otp` on the
> live server to watch the new lookup run. The call was blocked as a live write,
> and it was not worth working around — a registered number would have texted a
> real customer. The path is covered by the local suite and by the scan above.
