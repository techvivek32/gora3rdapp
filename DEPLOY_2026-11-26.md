### The new code is actually live, not just booted

Compiled backend: `mobile-verification.util.js` and `guest-otp.dto.js` present;
`assertMobileVerified` ×1, `settleWithdrawalTx` ×3, `roundTripPricePerKm` ×4,
`vehiclePricesRoundTrip` ×1, `resolveReturnDate` ×2.

New routes probed with an **empty body**, so validation rejects them before any
SMS is attempted: `/auth/guest/send-otp` → **400**, `/auth/guest/verify-otp` →
**400** (404 would have meant missing). No OTP was sent to anyone.

Shipped web bundle carries `Clear your name`, `Clear mobile number`,
`Clear pickup point`, `Use a different number`, `Send OTP`. Admin bundle carries
`Round Trip`, `roundTripPricePerKm`, `vehiclePricesRoundTrip`.

Two things that look like failures and are not:

- `roundTripPricePerKm` appears **0 times** in the live `/home-content/cab-categories`
  payload. Correct: existing categories were created before the field existed, so
  it is not stored on them and the API omits it. The fare code reads it as 0 and
  falls back to the one-way rate — which is the whole point of the design.
- `vehiclePricesRoundTrip` appears **0 times** in the compiled
  `settings.service.js` / `settings.controller.js`. It is only an inline
  TypeScript type annotation there, and those are erased at compile time. The
  service does `{ ...data }` → `$set`, so the field persists; the schema carries
  the `@Prop`. Proven separately by `rt_persist_test.js` (13/13).

## ⚠️ Read before setting any round-trip price

The app is still on the old build. An old app **ignores** `roundTripPricePerKm`
and prices a round trip at the one-way rate.

So the moment a round-trip price is saved in admin, **the website and the app
will quote different fares for the same trip**. Either hold off on setting
round-trip prices until the new APK is live, or accept the gap knowingly.

Nothing else diverges: with no round-trip price set, app and website agree
exactly, as they did before this deploy.
